# Sentinel Auth v3.3 — M11.3 Security Hardening

> **Status:** READY
> **Branch:** `feature/m11-security-hardening`
> **Baseline:** `origin/dev` @ `88786d6` (after M11.2 PR #14)
> **Date:** 2026-11-06

This report records the M11.3 security-hardening milestone: what was
verified, what was actually broken and fixed, what was already correct, and
what is still open.

The scope rule for this milestone was strict: **only real gaps in the
existing system** were fixed. No business logic was changed, no new
architecture was introduced, and no feature was added. Policy Create/Edit
was deliberately left out — see Section 7.

---

## 1. How the verification was done

The findings below are not read off the source. Each one was reproduced
against the running system:

* The CORS finding was proved with a live `curl` against the running
  monolith (`Origin: https://evil.example.com` + a `Cookie` header).
* The RBAC matrix was proved with real HTTP calls carrying real bearer
  tokens minted by the login endpoint, against a disposable PostgreSQL.
* The refresh-concurrency behaviour was proved with real concurrent
  transactions (25 rounds, a barrier-synchronised double refresh).
* The readiness semantics were proved by counting the rows in
  `inference_logs` before and after the probe.

## 2. Confirmed security gaps (fixed in this branch)

### 2.1 Wildcard CORS reflected any origin with credentials

**Evidence.** The monolith was configured with
`allow_origins=["*"]` together with `allow_credentials=True`. Starlette
therefore reflected an arbitrary `Origin` back whenever the request
carried a `Cookie` header:

```
$ curl -i -H 'Origin: https://evil.example.com' -H 'Cookie: session=attacker' ...
HTTP/1.1 200 OK
access-control-allow-origin: https://evil.example.com
access-control-allow-credentials: true
```

Any website could therefore read the authenticated responses of a signed-in
analyst.

**Fix.** `app/cors_config.py` replaces the wildcard with a configurable
allow-list read from `CORS_ALLOWED_ORIGINS`. The default is the origins the
local deployment is served at (`http://localhost:8000`,
`http://127.0.0.1:8000`), so the default surface is **not** wider than
before. The module:

* refuses a wildcard entry outright (`CORSConfigurationError`);
* normalises a trailing slash and lower-cases the scheme and the host;
* rejects an entry that is not a full `scheme://host[:port]` origin;
* rejects an entry that carries a path.

A preflight from an unlisted origin now answers **400**, and a normal
request from an unlisted origin gets **no** `Access-Control-Allow-Origin`
header at all. `scripts/deploy_local.sh` applies the same rule before the
container is started, and `.env.example` documents the variable.

### 2.2 `/ready` was a static response

**Evidence.** `/ready` returned `{"status": "ready"}` without consulting
any dependency. An orchestrator therefore routed traffic to a process whose
databases were unreachable, and the deployment verification had to prove
reachability through a *separate* mechanism.

**Fix.** `app/readiness.py` implements a dependency-aware probe:

* one bounded, read-only `SELECT 1` per bounded context (Core, Detection,
  ML) under a 2-second monotonic deadline;
* an unreachable database → **503** `{"status": "not_ready", ...}`;
* a missing ML **artifact** (the registry answered, the file does not
  exist) → **200** with `status: "ready"` and
  `checks.ml_artifact.status: "degraded"`, because the Detection Engine
  falls back to a rule-only score and can still serve traffic;
* a 2-second TTL cache for *successful* probes only, so a tight
  health-check interval does not hammer PostgreSQL while a recovery is
  still reported immediately;
* no row is ever written — proven by comparing the `inference_logs` count
  before and after the probe.

`/health` stays a strict liveness probe with zero dependency checks, so a
database outage never makes an orchestrator restart a healthy process.

### 2.3 The application started with an unusable internal secret

**Evidence.** `.env.example` promised that the application "will refuse to
start if `INTERNAL_SECRET` was absent, empty, or set to a placeholder". It
did not: the app imported and started normally, and only answered **503**
when an internal endpoint was actually invoked. Worse, the *outbound*
service calls (the pre-token risk check, the login-event delivery) fail
**open** in that state — so a deployment that lost its secret silently ran
with its service-to-service boundary disabled.

**Fix.** `app/main.py` validates the secret in the `lifespan` handler,
before any traffic is accepted, and raises `InternalSecretConfigurationError`
(a `RuntimeError` subclass). The secret value is never logged and never
included in the error message — only the reason for the rejection.

### 2.4 The template secret from `.env.example` was accepted

**Evidence.** `internal_auth.py` rejected exactly one placeholder string,
`"changeme-in-production"`. The value the repository actually ships in
`.env.example` is `change-me-to-a-secret-at-least-32-chars` — 38
characters, so it passes the length rule and was accepted by the
application. `scripts/deploy_local.sh` refused it (`change-me*`), so the
script and the application disagreed about what a usable secret is.

**Fix.** `app/internal_auth.py` now refuses any secret that still carries a
template placeholder prefix (`change-me`, `changeme`, `replace-me`,
`placeholder`, `your-`, `secret`, `password`) — the same rule the
deployment script applies. A secret produced by
`secrets.token_urlsafe(32)` is accepted.

### 2.5 The test suite sent the developer's real secret to the application

**Evidence.** `tests/conftest.py` used `os.environ.setdefault("INTERNAL_SECRET", …)`.
`setdefault` keeps a value that is already present, so a developer who had
`INTERNAL_SECRET` in the shell — for example loaded from the local `.env` —
had **their real deployment secret** used for every internal-boundary test.
The suite then asserted against a different value, so every internal test
failed with 401, and the developer's own secret travelled inside test
requests and log output.

The same failure reproduces on the untouched baseline (`origin/dev` @ `88786d6`):
31 of the internal-boundary tests fail when `INTERNAL_SECRET` is exported.

**Fix.** The fixture now *forces* the test secret and restores the previous
value on teardown. The suite is now independent of the developer's shell
environment, and no real secret can leak into a test request.

### 2.6 A blackholed database could hang the readiness probe indefinitely

**Evidence.** The probe's 2-second deadline was only checked *between* the
per-context checks. A single `SELECT 1` against a database host that
**drops** the packets (rather than refusing them) therefore hung on the
operating system's own TCP timeout — measured at **more than 60 seconds**
here, with no answer at all:

```
$ python3 -c "... SELECT 1 against 10.255.255.1 (non-routable) ..."
# timeout after 60s, no answer
```

The deployment script also refused a wildcard `FORWARDED_ALLOW_IPS`, and
`app/db.py` created its engines with `create_engine(url, pool_pre_ping=True)`
— **no connect timeout**. A probe that blocks for a minute is worse than no
probe: the orchestrator sees a hung health check instead of an answer.

**Fix.** Two halves, because there are two ways a database can go silent:

* `app/db.py` — every engine is created with a driver-level
  `connect_timeout` (`CONNECT_TIMEOUT_SECONDS = 2`). A host that never
  completes the handshake now fails in 2 seconds instead of hanging for the
  OS timeout. The argument is only passed to the PostgreSQL driver, because
  another dialect's driver would reject the unknown keyword.
* `app/readiness.py` — the probe statement runs under a server-side
  `SET LOCAL statement_timeout` derived from the remaining budget, so a
  server that **accepts** the connection and then stops answering is cut
  off too.

Measured after the fix: the same blackholed database answers in **2.02 s**,
inside the 2-second budget, with `status: "not_ready"` and each context
reported as `unavailable`.

### 2.7 The readiness probe held the event loop for its whole budget

**Evidence.** `/ready` is an `async def` endpoint, but the probe talks to
PostgreSQL through the **synchronous** SQLAlchemy driver, so it ran
directly on the event loop. Measured with a ticker running concurrently:

```
the blocking probe held the event loop for 2.03s
```

While the probe waited for an unreachable database, **every other request
in the process** — a login, the SOC alert list — was stalled behind it,
even though the process itself was perfectly healthy. This is the worst
failure mode for a health endpoint: the check that is supposed to protect
the service was the thing that blocked it.

**Fix.** `app/readiness.py` gained `readiness_payload_async()`, which runs
the probe in a worker thread via Starlette's `run_in_threadpool`, and
`app/main.py` awaits it. The endpoint answers exactly as before.

Measured after the fix: the same probe answers `503` in 2.02 s while the
maximum event-loop tick gap is **0.053 s** — the loop keeps serving
traffic throughout.

The probe's session is also rolled back before it is closed, so a
statement timeout cannot leave an open transaction on the pooled
connection.

### 2.8 The ML registry query could outlive the probe's deadline

**Evidence.** `_check_ml_artifact()` queried the model registry with **no
deadline and no statement timeout**. The query reads the `model_versions`
table, so a transaction holding an `ACCESS EXCLUSIVE` lock on it blocks the
reader indefinitely — the server queues it behind the writer — while
`SELECT 1` keeps answering normally.

That makes the failure invisible to the database check: the probe reported
the ML database as `ok` and then hung on the registry query. Reproduced
against the running system:

```
Transaction A: LOCK TABLE model_versions IN ACCESS EXCLUSIVE MODE
Transaction B: SELECT 1 -> 1          (the database answers fine)
/ready         -> no answer at all    (killed after 90 s)
```

**Fix.** `_check_ml_artifact()` now takes the same `_Deadline` as the
database checks:

* when the deadline has already been spent, the registry query is **not
  started at all**;
* otherwise the query runs under a server-side `statement_timeout`
  derived from the remaining budget;
* the session is always rolled back and closed.

The three outcomes are kept apart:

| Situation | Result |
|-----------|--------|
| The artifact is not configured, or its file is missing | `degraded` — the Detection Engine falls back to a rule-only score, so the service stays **ready** |
| The registry could not be queried (timeout, unreachable database, a locked table) | `unavailable` — the artifact state is **unknown** |
| The deadline was already spent | `unavailable` |

An **unknown** artifact state makes the probe **fail closed**: `/ready`
answers `503`. Reporting it as "the artifact is merely missing" would turn
a broken dependency into a healthy answer — the probe would claim the
service is ready on an assumption it could not verify.

## 6. Remaining risks

| # | Risk | Severity | Mitigation |
|---|------|----------|------------|
| R1 | The CORS allow-list has to be extended explicitly for a separate front-end. A front-end that is not listed receives no CORS headers and appears broken. | Low (fail-closed) | `.env.example` documents the variable; the error at startup names the rejected entry. |
| R2 | The readiness probe caches a *successful* result for 2 seconds, so a database that fails immediately after a successful probe is reported up to 2 seconds late. | Low | The cache applies to successes only; failures are never cached. The interval is far below any health-check cadence. |
| R2b | A request that reaches a database **after** the connection is established can still outlast the probe's `statement_timeout` if it runs a heavy query — the timeout applies to the probe's own statement, not to the application's traffic. | Low | The probe's budget is a probe concern. The application's own queries are bounded by the pool's `pool_timeout`, which is unchanged from the baseline. |
| R2c | The probe runs in a worker thread, so a *thread pool* exhaustion under extreme load could delay the readiness answer. | Low | The thread pool is Starlette's default (40 threads); the probe is called by the orchestrator, not by user traffic. |
| R3 | The internal secret is now a startup requirement. A deployment that starts the app without it now **fails to start** instead of serving degraded traffic. | Low (intended) | The error message states the reason and how to generate a valid secret. `deploy_local.sh` already required a 32-character secret, so no working deployment changes behaviour. |
| R4 | The ML artifact is still missing in the demo deployment, so `/ready` reports `degraded`. That is the honest state: the Detection Engine falls back to a rule-only score. | Known, pre-existing | The demo deployment ships a *staged* placeholder on purpose; the artifact must be promoted by a separate model pipeline. |
| R5 | The RBAC matrix is verified against the monolith's in-process routes. The three-service split (backlog item "Three independent services") would have to re-establish the same boundary over the wire. | Medium (future) | The internal boundary is already enforced by the `X-Internal-Secret` header, which survives the split unchanged. |

## 7. Policy Create/Edit — explicitly deferred

Policy Create/Edit was **not** implemented in this branch. Mixing a new
authorisation surface into a hardening branch would make the diff
unreviewable and would add endpoints while the existing ones were still
being verified.

The item is carried in the implementation backlog of
`docs/DECISIONS-SYSTEM-v3.3.md` (Section 10.4 note and backlog item **F-1**)
and is to be implemented on a separate feature branch, reusing the role
matrix that the listing and activation endpoints already enforce.

> **Update (2026-11-07).** F-1 has since been implemented on the feature
> branch `feature/f1-policy-crud` — see `docs/DECISIONS-SYSTEM-v3.3.md`
> §10.5 and `docs/DECISIONS-DETECTION-v3.3.md` §6.1. This document remains
> the record of the M11.3 hardening branch only.

## 8. Verdict

**READY.**

Every confirmed gap has a fix and a test. The full suite, the deployment
verification and the real HTTP smoke run are green with zero failures and
zero skips. The remaining risks are either deliberate trade-offs (R1, R3),
pre-existing and documented (R4), or belong to a future architecture
milestone (R5).
